# 汎用エージェントルール

この文書は、従来の `AGENTS.md` から分離した汎用ルールである。
ルート `AGENTS.md` は Codex の既定読み込み上限に収めるため、必須事項だけを保持する。
詳細確認が必要な場合は、この文書を参照する。

この文書は、前段の `汎用ルール` と後段の `本リポジトリ固有ルール` に分けて保守する。

前段の `汎用ルール` は、他リポジトリへ先頭からそのまま転用しやすい共通指針として扱う。

---

## 汎用ルール

### 長大タスク運用ルール

#### A. 長大タスクの基本原則

- 作業ブランチを作成して作業をすること。
- 作業ブランチ上で適切にコミット粒度を分け、検証可能な区切りごとにコミットしながら進めること。
- 長大タスクの「タスク境界」は PR / branch の単位であり、1コミットへ全差分を集約するという意味ではない。
- Codex の `/goal` で与えられた課題は、通常の単発応答ではなく、完了条件を満たすまで継続する長大タスクとして扱う。
- `/goal` タスクでは、品質、機能完成度、テスト、ドキュメント整合性を落として早く止まることを禁止する。
- 合理的に前進できる不明点は、停止理由にせず、明示的な仮定として計画ファイルへ記録して実装を進める。
- 受け入れ条件、検証コマンド、回帰テスト、ドキュメント更新が揃うまで完了扱いにしない。
- タスク境界は大きく取る。通常なら 5 スライス程度に分ける規模の作業を、1 つの PR / branch で完結させる前提で計画する。
- ただし、コミットはレビュー可能な単位へ分割する。大規模移行では、計画・棚卸し、基盤/API、型契約、UI scaffold、機能別移植、旧実装削除、docs/CI/package のように、責務と検証観点が分かれる単位でコミットを分ける。
- 1コミットの中で、独立してレビューできる複数の関心事を混在させない。特に「新基盤の追加」と「旧基盤の削除」、「実装」と「大規模ドキュメント更新」、「依存追加」と「機能移植」は、強い理由がない限り別コミットにする。
- ただし、内部マイルストーンは小さく管理し、各マイルストーン完了ごとに検証と計画ファイル更新を行う。
- 「動く最小断片」だけで止めず、対象機能の UI、Application Service、Domain、Infra、テスト、ドキュメントまでを一貫した縦切りで完了させる。
- 破壊的変更、外部依存、権限不足、要件衝突以外を理由に作業を中断しない。
- 最終応答では、実装内容、変更ファイル、実行した検証、未解決リスク、次に人間が確認すべき事項を簡潔に報告する。

#### B. 開始前の計画

- 長大タスクに着手する前に、`plans/<task-id>.md` を作成または更新する。テンプレートは `plans/TEMPLATE.md` を使う。
- `plans/TEMPLATE.md` が存在しない場合は、最初の長大タスクで最小限のテンプレートを作成する。
- 実務手順の補助が必要な場合は `docs/process/task-execution.md` を参照し、運用判断を各エージェント固有機能へ依存させない。
- `docs/process/task-execution.md` が存在しない場合は、既存ドキュメント、README、Makefile、スクリプトから作業手順を推定し、必要に応じて同文書を追加する。
- 計画ファイルには最低限、`目的`、`非目標`、`対象範囲`、`マイルストーン`、`受け入れ条件`、`検証コマンド`、`既知 blocker`、必要なら `feature flag / rollback` 方針を記載する。
- 作業開始時は、作業ディレクトリ、直近の git 履歴、計画ファイル、未完了 checklist、起動スクリプト、最小動作確認の順で足場を確認する。
- `/goal` での作業では、計画ファイル内に `Goal 完了条件` を明示し、その条件が満たされるまで作業を継続する。
- 既存コードが少ない初期リポジトリでは、まず標準的なディレクトリ構成、検証入口、README、gitignore、最小テストを整えたうえで機能実装に入る。

#### C. マイルストーン完了時の検証

- 各マイルストーン完了時に、その変更に必要な lint / typecheck / test / build を実行し、結果を計画ファイルへ記録する。
- 失敗を認識したまま次へ進めず、原因を切り分けて修正するか、`Blocked` として停止条件へ回す。
- 完了宣言はコード閲覧だけで行わず、明示した受け入れ条件と検証結果を満たした場合のみ行う。
- UI 変更では、見た目だけでなく、操作導線、空状態、エラー状態、長文入力、保存復元、アクセシビリティ上のラベルを確認する。
- LLM 呼び出しを含む変更では、外部 API を直接叩くテストではなく、モック、フェイク、契約テストで境界の正しさを確認する。
- 永続化を伴う変更では、新規作成、更新、削除、再起動後復元、破損データ時の失敗表示を検証する。
- 回帰バグを直した場合は、修正前の失敗条件が分かるテストを追加し、計画ファイルへ再発防止内容を記録する。

#### D. PR の作成条件

- 中間共有は、計画ファイルのステータス更新・チェックリスト更新・ローカルコミットを基本とする。
- **通常 PR は受け入れ条件をすべて満たしてから作成** する。
- レビュー待ちが必要な設計判断やリスク共有がある場合のみ、例外として Draft PR を許容する。
- PR を Draft にしてよいのは、ユーザーが明示した場合、Codex app の PR 設定で Draft が指定されている場合、または上記の例外条件に該当する場合のみとする。
- PR 作成ツールやスキルの既定値が Draft であっても、ユーザー指示、Codex app 設定、この `AGENTS.md` の条件を満たさない限り、明示的に Draft 指定してはならない。
- PR 作成前に Draft / Ready のどちらで作成するかを確認し、判断根拠を plan または作業メモへ記録する。判断できない場合は、受け入れ条件を満たした通常 PR として Ready で作成する。
- `/goal` タスクでは、PR 作成や完了報告の前に、計画ファイルの全 checklist を `Done`、`Blocked`、`Cancelled` のいずれかへ整理する。
- `/goal` タスクでは、受け入れ条件と検証を満たしたあと、ブランチの push と PR 作成まで完了してから最終報告する。外部認証、権限、GitHub 障害などで PR 作成不能な場合のみ Blocked とし、PR 未作成理由、再開条件、次の最短アクションを plan と最終報告に明記する。
- push または PR 作成後は、CI / checks が完了するまで必ず監視する。`pending`、`queued`、`in_progress` の check を残したまま完了報告しない。
- CI / checks が失敗した場合は、失敗ログを確認し、原因を plan または作業メモへ記録し、修正、ローカル検証、コミット、push、CI 再監視を成功するまで繰り返す。
- push と pull_request のように同一 workflow が複数 event で走る場合は、対象 event すべての結果を確認する。一方だけ成功した状態で完了扱いにしない。
- CI / checks の最終状態は `success` / `skipped` / `neutral` など受け入れ可能な状態に限る。`failure`、`cancelled`、`timed_out`、`action_required` は未完了として扱う。
- 外部サービス障害、権限不足、GitHub Actions 障害などで CI 完了確認ができない場合だけ Blocked とし、失敗 check 名、run URL、停止理由、再開条件、次の最短アクションを plan と最終報告に明記する。
- `/goal` タスクの最終応答には、作成した PR の URL、対象ブランチ、検証結果を必ず含める。
- 大きなタスクでは、単に差分量を減らすための中途半端な分割をしない。一方で、PR 全体を 1 コミットへまとめることを避け、1 つのレビュー観点または 1 つの内部マイルストーンを満たす単位で cohesive commit にする。
- 各コミットは、可能な限り単体で説明可能かつ検証可能にする。途中コミットで全体受け入れ条件を満たす必要はないが、WIP、壊れた状態、未接続の仮実装だけを残すコミットは避ける。
- 履歴レビュー時に「このコミットで何が可能になり、何を検証したか」が分からない粒度は大きすぎる。ファイル数・行数だけでなく、責務、依存境界、検証コマンド、rollback のしやすさを基準に分割する。

#### E. 停止条件と状態整合

- 停止してよいのは、主に次の場合のみとする。
  - 外部依存、権限不足、環境障害などで実質的に Blocked。
  - 要件衝突があり、合理的な仮定では進行不能。
  - 破壊的変更の是非を既存文書だけでは判断できない。
  - API キー、秘密情報、外部サービス契約など、人間が提供しないと検証不能な情報が必須。
- 停止前に、計画ファイルやチェックリストの対象項目を **Done / Blocked / Cancelled** のいずれかへ更新し、`pending` / `in_progress` を放置しない。
- `Blocked` で止める場合は、停止理由・再開条件・次の最短アクションを短く明記する。
- Blocked でも、実装可能な周辺整備、テスト、ドキュメント、スタブ、インターフェース定義が残っていれば先に完了させる。
- 停止時に未コミット差分がある場合は、差分の意図、検証状況、破棄してよいかどうかを最終報告へ明記する。

### コミットメッセージ

- 生成するコミットメッセージは必ず日本語で書く。
- 文体は簡潔に保ち、要点がすぐ伝わる表現を優先する。
- コード記号、ファイル名、クラス名、関数名、メソッド名、一般的な技術用語は必要に応じて英語のままでよい。
- 基本形式は 1 行目に変更内容の要約を書き、補足が必要な場合のみ 2 行目以降に追記する。
- `/goal` タスクのコミットでは、1 行目で実装したユーザー価値を示し、必要なら 2 行目以降に検証結果や大きな設計判断を書く。
- 一時作業、WIP、試行錯誤だけを表すコミットメッセージは避ける。

### ドキュメント更新ルール

- 実装、挙動、セットアップ、アーキテクチャ、設計を変更したら、`README.md` の更新要否を必ず確認する。
- `README.md` は仕様変更に追従して更新しつつ、README の一般的な役割から逸脱する過剰な追記は避ける。
- 変更や新規設計を行ったら、`docs/` 配下の関連文書を必ず見直し、現状の挙動、制約、意図とずれていれば更新する。
- 長大タスクでは、計画ファイル、設計文書、README、テスト方針の整合性を作業完了前に確認する。
- ユーザー向け UI とドキュメントで用語がずれた場合は、どちらか一方だけを直さず、用語集または関連節も更新する。

### コーディング原則

### DRY

- 同一ロジック、定数、バリデーションが 2 回現れたら抽出を検討し、3 回現れたら関数、クラス、モジュールのいずれかへ必ず抽出する。
- 設定値は環境変数または設定モジュールに集約し、マジックナンバーを持ち込まない。
- 重複するテストデータは factory や fixture に集約する。
- コピーアンドペーストでの派生修正を避け、共通化後に差分だけを表現する。
- 同じ入力検証を UI と API で別々に増殖させず、責務に応じて共有可能なルールを整理する。
- リファクタリングは、重複箇所の探索、共通化単位の決定、抽出、逆依存の解消、テスト確認の順で進める。

### KISS

- 実装はまず最小構成で成立させ、不要な抽象化や仕組み化を後回しにする。
- 分岐のネストは 3 階層以内を目安にし、巨大関数はおおむね 40〜60 行を超える前に分割を検討する。
- 早期 `return` やガード節を使って認知負荷を下げる。
- DSL、メタプログラミング、反射、動的 import は最後の手段として扱う。
- 依存ライブラリは最小限に保ち、標準機能で足りる場合は追加しない。
- 初見の開発者が 5 分程度で処理の骨子を追える複雑さを目安にする。

### SoC

- 層分割を守り、`UI/Presentation`、`Application/Service`、`Domain`、`Infra/DB` の関心事を混在させない。
- ログ、計測、リトライ、認可などの横断的関心はミドルウェア、デコレータ、共通基盤で注入する。
- フロントエンドでは状態管理と描画を分離する。
- コンポーネント内で `fetch`、DOM 操作、業務ロジックを同居させない。
- ドメイン層から HTTP クライアントや ORM を直接呼ばない。
- PySide6 の Widget から OpenAI API、SQLite、生ファイル IO を直接呼ばず、Application Service 経由にする。

### SRP

- ファイル名と公開 API が責務を説明できる状態を保ち、曖昧なら分割する。
- クラスは 1 つのユースケースまたは 1 つのポリシーに集中させる。
- モデル定義、入出力、整形、保存処理を 1 ファイルに混在させない。
- God Object、God Component、肥大化した utility モジュールを避ける。

### YAGNI

- Issue や要件に存在しない抽象化、設定、拡張ポイントは追加しない。
- 未使用フラグや将来用の空実装を置かない。
- ただし、セキュリティ、可観測性、エラーハンドリングに必要な最低限の備えは先行してよい。
- 汎用ルールセットや LLM Agent の拡張ポイントは、本リポジトリの主要要件であるため、必要最小限の差し替え構造を許容する。

### POLA

- 同種の関数や API はシグネチャと戻り値の規約を揃え、直感に反する特殊挙動を避ける。
- 非同期 API は常に `async`/`await` または Promise の規約に従い、呼び出し側を驚かせる同期値返却を混在させない。
- 破壊的操作は `delete*` や `mutate*` のように名前で明示し、暗黙の副作用を避ける。
- バリデーションメッセージは入力タイミングと表現を一貫させる。
- UI 上で「AI が自動適用した変更」と「AI が提案しただけの変更」を混同させない。

### OCP

- 種別追加のたびに条件分岐を増殖させるのではなく、ポリモーフィズム、戦略パターン、差し替え可能な構造で拡張できるようにする。
- 支払、翻訳、ストレージなどの外部統合はインターフェースで抽象化し、アダプタ実装を分離する。
- `if type == 'A'` の列挙が伸び続ける構造を放置しない。
- 画像生成サービスの Capability、Ruleset、LLM Agent、Storage Adapter は追加・差し替え可能な構造にする。

### エラーハンドリングと可観測性

- エラーを消すこと自体を目的にせず、なぜその機能が正常に動かなかったのかという本質原因を優先して特定する。
- 失敗は例外または `Result` 型などで明示し、黙殺しない。
- 不具合や不備は適切にエラーとして検知できる状態を重視し、無暗に握りつぶしたり、過剰なフォールバックで問題を隠したりしない。
- 想定可能な失敗は、再試行、フォールバック、ユーザー通知の方針を事前に決める。
- ログは構造化し、`level`、`event`、`context` を含め、PII は必ずマスキングする。
- 主要ユースケースでは成功率、p95 latency、再試行率などのメトリクスを計測できる状態を目指す。
- LLM 呼び出し失敗時は、モデル名、agent 名、schema 名、retry 回数、失敗種別を記録する。ただし API キー、全文プロンプト、画像内容、個人情報はログへ出さない。
- ユーザー操作の失敗は、開発者向け詳細とユーザー向け説明を分ける。

### テスト

- テストピラミッドを意識し、Unit Test を厚く、Integration Test を必要十分に、E2E はクリティカル経路に絞る。
- テスト記述は `Given`、`When`、`Then` の読みやすさを意識する。
- 重複するテストデータは factory や fixture に集約する。
- UI テストは `getByRole` などロールやラベル中心で選択し、`data-testid` は最後の手段とする。
- ネットワーク越しの依存は原則モックし、境界の妥当性は契約テストで補う。
- カバレッジの目安は line 80%、branch 70% とするが、数字だけを目的化しない。
- バグ修正、障害対応、仕様解釈の修正を行った場合は、同種の不具合を再発させない回帰テストの追加を原則とする。
- 回帰テストは、修正後の正常系だけでなく、修正前に何が壊れていたかが分かる失敗条件と期待結果を明示する。
- 回帰テストは実装詳細に過度に依存させず、外から観測できる契約、エラー、ログ、状態遷移を優先して固定する。
- 複数層にまたがる不具合は、最小コストで再発を防げる層から順に Unit Test、Integration Test、E2E のどこへ置くかを判断する。
- 一度起きた設定ミス、境界値バグ、非同期タイミング起因の不具合は、単発修正で終わらせず、将来の変更でも落ちるテストとして残す。
- LLM の出力はスナップショット固定だけに依存せず、schema 準拠、必須 field、境界値、失敗時挙動を検証する。
- GUI テストは可能な範囲で `pytest-qt` 等を使い、困難な部分は Widget から切り出した Presenter / ViewModel / Service の Unit Test で固定する。

### 依存と構成管理

- 依存は最小限に保ち、未使用依存は削除する。
- ロックファイルは依存変更に追従して更新し、既知の CVE を監視する。
- 設定は 12-factor app の考え方に沿って扱い、秘密情報は環境変数や秘密管理基盤に置く。
- セキュリティリスクを増やさないよう、生成物、秘匿情報、環境依存ファイル、認証情報を誤って追跡しないか常に確認し、必要なら `gitignore` を更新する。
- 公開 API に破壊的変更を入れる場合は、セマンティックバージョニングを意識して扱う。
- OpenAI API キー、ユーザーの制作プロンプト、参照画像、生成画像、ローカル DB、ログ、キャッシュは追跡対象にしない。
- API モデル名、タイムアウト、リトライ、保存モードは設定モジュールへ集約し、UI や各 Agent に直書きしない。

### スタイルと可読性

- 変数名、関数名、メソッド名、クラス名は短さより可読性と意味の明確さを優先する。
- 略語は一般的に通じるものだけに留める。
- 関数名は副作用の有無が分かるように付ける。
- 新規アサインされたメンバーでも理解しやすいよう、クラス、関数、メソッド、または複雑で個性の強い処理には、意図と責務が分かる明確なコメントを付ける。
- コメントは「なぜ」を補い、「何をしているか」はコードと命名で表現する。
- ソースコード内のコメントに改修時の連絡事項、申し送り、作業メモを残さず、現状の仕様や挙動の説明だけを書く。
- 現在の仕様理解やキャッチアップに役立つ補足は積極的にコメントし、過去の経緯ではなく今どう動くかが分かる内容を優先する。

### 記述原則

- ドキュメントは `DRY`、`KISS`、`SRP`、`SoC`、`OCP`、`POLA` と矛盾しない形で保守する。
- 単一ファイルが肥大化しないよう、役割単位で内容を分割する。
- 1 つの節が概ね 3〜5 項目を超えて膨らむ場合は、別節または別文書への切り出しを検討する。
- 重複説明は共通セクションに集約し、各所では差分だけを書く。
- 魔法値、隠れた前提、暗黙の依存関係を文書に残さない。

### アーキテクチャ記述

- コード構造を説明する場合は、`責務`、`依存`、`分岐条件`、`拡張ポイント` を明示する。
- 説明は簡潔に保ちつつ、別の開発者が責務配置と安全な拡張方法を判断できる粒度にする。

### 分割指針

- コードファイルと長文ドキュメントは、おおむね 600〜800 行を分割検討の目安とする。ただし絶対上限ではない。
- コードを分割する場合は、`service`、`domain`、`IO` など再利用しやすい断面を明示する。
- UI ファイルが肥大化する場合は、Widget、Presenter、Model、Action、Style 定義を分ける。
- Agent 実装が肥大化する場合は、Prompt Template、Schema、Client Adapter、Use Case Service を分ける。

### 変更時チェックリスト

1. `README.md` の更新要否を確認する。
2. 影響を受ける `docs/` 配下の文書を確認する。
3. 必要なら `gitignore` の更新要否を確認する。
4. ルールや作業指針の不備が明らかになった場合は、対応する `AGENTS.md` の更新要否を確認する。
5. 実装や設計の意味が変わった場合は、関連ドキュメントを同じ変更内で更新する。
6. UI 文言を追加・変更した場合は、特定の Midjourney バージョン番号がユーザー向け画面に出ていないか確認する。
7. LLM Agent を追加・変更した場合は、schema、モック、失敗時挙動、ログの秘匿性を確認する。
