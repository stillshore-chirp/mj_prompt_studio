# Issue 品質ゲート

Issueは「何を変えるか」だけを並べる作業メモではありません。第三者が、なぜ今必要か、何を根拠に判断したか、どの状態なら完了かを検証できる追跡単位です。

## 1. 適用範囲

新規Issueを作成する場合と、既存Issueを今回の主Issueとして採用する場合に適用します。Issueを省略できる条件はルート AGENTS.md とGitHub配送Skillを優先します。

## 2. 必須内容

該当する .github/ISSUE_TEMPLATE/ を使い、少なくとも次を記載します。

1. 背景と判断理由: なぜ必要か、なぜ今か、対応しないと誰がどこで困るか。
2. 根拠と不確実性: 確認済み事実、ユーザー提示情報、code・公式仕様・log・実dataの出典、仮説・推定・未確認事項。
3. 現状の問題と影響: 現在の挙動または制約、利用者・運用・保守・data・securityへの影響。
4. 現在と対応後のユーザー体験: 対象ユーザー、利用文脈、目的、現在の認識・負担・感情・体験状態、対応後に理解・判断・実行・回復できること、その根拠区分。
5. 目的と期待する成果: 実装項目ではなく作業後に成立させたい状態。
6. 対応範囲と非対象: 今回行うこと、行わないこと、その理由。
7. 受け入れ条件と検証方針: 第三者がPass / Failを判定できる条件と、test・画面・log・文書・手動確認。
8. リスクと未確認範囲: 既存挙動への影響、実行できない検証、完了後の不確実性。

## 3. 事実・判断材料・仮説の分離

| 種別 | 書き方 |
|---|---|
| 確認済み事実 | 何を、どの証跡で確認したか |
| ユーザー提示の判断材料 | 依頼時の情報であり、repository側で再検証したか |
| 判断 | どの事実・目的・制約から方針を選んだか |
| 仮説・推定 | 未確認であることと確認方法 |
| 未確認事項 | 確認できない理由、影響、次の最短action |

外部評価や第三者資料は、出典だけで確認済み事実へ格上げしません。現行仕様や高risk判断は、可能な限り公式資料、code、test、log、実dataで確認します。

## 4. ユーザー体験

現在と対応後は、同じ対象ユーザーと利用文脈を基準に対で記載します。機能名、変更file、実装方法だけで代替しません。

### 現在のユーザー体験

- 対象ユーザー、利用文脈、達成したいことを特定します。
- ユーザーが実際に見聞きし、判断し、操作し、待機し、失敗し、回復していることを書きます。
- 認識、迷い、負担、不安、安心、信頼と最終的な体験状態を、ユーザー申告、実ユーザー観察、観測事実からの推定、未確認の仮説へ区分します。

### 対応後に目指すユーザー体験

- 同じ対象ユーザーと文脈で、何がどう変わるかを書きます。
- より確実に理解、判断、実行、回復できることを書きます。
- 手数や待ち時間だけでなく、認識、負担、安心、信頼の変化を受け入れ条件へ接続します。

### 体験が直接変わらないIssue

調査、内部改善、保守、ガバナンスでも記載を省略しません。「直接的なユーザー体験の変化はない」と理由を明記し、直接の対象が開発者や運用者なら、その対象を明示します。

## 5. 既存Issue

必須内容が不足する既存Issueは、実装前に本文を更新するか、変更できない理由とともにcommentで理由、根拠、成果、非対象、受け入れ条件、riskを補います。実装中にscope、判断、事実、未確認事項が変わった場合もIssueを更新し、PRだけに重要な判断を閉じ込めません。

## 6. 公開安全性

Issueは公開され得る文書です。secret、credential、PII、prompt全文、画像、実log原文、local path、追跡可能IDを貼りません。

公開できない根拠は、証跡種別、公開可能な観測事実、判断への影響、非公開範囲、必要な次の確認へ要約します。詳細は [docs/security-publication-checklist.md](../security-publication-checklist.md) を正本とします。

## 7. Issue / PRの日本語品質

IssueとPRのtitle・本文は日本語を原則とします。固有名詞、製品名、library名、code identifier、version/path、GitHub構文、一般的なIssueカテゴリのprefixは原表記を維持できます。対象と変更または問題が判別できる具体性を持たせ、改善、対応、updateだけのtitleにしません。

## 8. レビュー指摘を別Issueで追跡する場合

レビュー結果を主因として別Issueを作成する場合だけ、titleを [レビュー指摘] <日本語要約> とし、レビュー指摘 labelを付けます。本文に由来PR・review、severity、観測事実、影響、別追跡の理由、現在と対応後のUX、scope、acceptance、verification、公開安全性を記載します。

同一PRのレビュー修正は主Issueを継続して追跡し、別Issueへ分けません。根拠不足でレビュー起因と断定せず、P0、P1、security、secret、data integrity、受入証跡の矛盾は別Issue化してもblockingを解除しません。

## 9. Pass / Fail

### Pass

- 第三者が理由、根拠、成果、範囲、非対象、受け入れ条件、検証、riskを読み取れる。
- 確認済み事実と未確認事項、現在と対応後の体験、根拠区分を比較できる。
- 受け入れ条件が観測可能な結果で、公開してはいけない情報を含まない。

### Fail

- 変更file、実装項目、「改善する」だけで、理由、対象、体験差、受け入れ条件が分からない。
- 未確認の感情、外部情報、ユーザー提示情報、仮説を確認済み事実として断定している。
- 非対象、検証できない範囲、残るriskがなく、完了を客観的に判定できない。

FailのIssueを主Issueとして実装を開始しません。必要な判断材料を補ってから開始します。
