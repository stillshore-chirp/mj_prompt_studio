# 証跡と完了ゲート

## 1. 必須証跡

UI/UX変更では、変更画面・状態、ユーザー価値、state matrix、初見シミュレーション、アクセシビリティ、視覚階層、コピー、熟練者効率、満足感・信頼感、反証レビュー、実行・未実行検証、残リスクを記録します。

UI変更PRでは、該当画面・状態ごとの変更前と変更後のスクリーンショットをPR本文へ添付します。通常状態だけでなく、変更に関係する空、待機、error、狭幅なども対象です。

## 2. 成果物の判定

- ユーザー価値: 対象、文脈、目的、支援タスク、UIがない場合の困り事を説明できる。
- state matrix: 該当状態で、表示、理解、次行動、回復、a11y通知、証跡、Pass/Failを示す。
- 初見: 画面目的、現在地、最初の行動、結果予測、回復が分かる。
- アクセシビリティ: 自動検査だけでなく主要taskのkeyboard、focus、label/name、状態通知を確認する。
- 効率: 主要反復taskの手数、再入力、再選択、再試行、復帰、近道を確認する。
- 信頼: 待機、成功、失敗、危険操作、保存、外部送信、削除のfeedbackを確認する。
- 反証: P0と証跡不足を落とすつもりで探す。

## 3. 完了ゲート

次をすべて満たした場合だけ完了扱いできます。

- P0がない。P1は同じ変更内で修正済み、または明示的な延期根拠がある。
- ユーザー価値と初見理解が成立する。
- state matrix、a11y、視覚階層、コピー、効率、信頼、反証レビューがある。
- UI変更PRの前後スクリーンショットが本文で確認できる。
- `make client-lint`、`make client-typecheck`、`make client-test`、`make client-build`、必要な`make e2e`と手動確認が成功するか、未実行理由と残リスクがある。
- 実施していない検証や実ユーザーテストを実施済みとしない。
- PRではpush/PR CI成功後のCodex review、review comment、未解決review threadを確認する。

## 4. 証跡を取得できない場合

取得できない検証、理由、代替確認、残リスク、次の最短確認を記録します。前後スクリーンショットを取得できないUI変更は、代替説明だけで完了にしません。

スクリーンショットにはAPI key、prompt全文、参照画像、生成画像、ローカルpath、ユーザー情報など機微情報がないことを目視し、公開安全性チェックを通します。

## 5. 推奨検証

lint、typecheck、unit/integration test、Playwright E2E、keyboard操作、axe等のa11y検査、狭幅、文字拡大、長文、視覚差分を変更範囲に応じて選びます。

## 6. 報告

`templates/completion-gate-report.md` と `templates/uiux-review-report.md` を使います。証跡はPR本文、plan、または `docs/ai-governance/reports/` のタスク固有reportへ残し、ユーザー資産を追跡しません。
