# UI/UXレビュー・フレームワーク

この文書は、AIエージェントがMJ Prompt StudioのUI/UXをreviewするための中心規約です。

## 1. 適用対象と所有境界

証跡の範囲は、表示場所ではなく、変更対象のUIと操作を誰が制御しているかで決めます。

| 対象面 | 例 | リポジトリが制御するもの | 適用するreview |
|---|---|---|---|
| アプリ本体UI | React client、製品の独自Web UI | layout、操作、状態、focus、accessibility、copy | 本文書の全review経路とアプリUI証跡 |
| GitHub共同作業面 | Issue / PR template、Issue / PR本文、repository Markdown、workflowの入力・説明 | 文言、項目、順序、必須性、Markdown、設定 | 内容・構造・表示・link・公開安全性の範囲に比例したreview |

ブラウザで表示されること自体は、アプリ本体UIである根拠になりません。GitHub共同作業面では、GitHubが提供していて変更していないlayout、keyboard操作、focus、loading stateまで検証対象に広げません。

GitHub共同作業面だけの変更でも、リポジトリが制御するcopyの明確さ、入力順、必須項目、送信前に必要な判断材料、Markdownの崩れ、link、公開安全性は確認します。対象面が混在する変更は、それぞれ別に判定し、GitHub側の確認を理由にアプリ本体UIの検証を省略しません。

## 2. UI/UX品質の定義

対象ユーザーが特定の文脈で目的を達成でき、その過程が分かりやすく、見やすく、操作しやすく、失敗しても回復でき、慣れれば速く、安心して使えることを品質とします。

アプリ本体UIの変更では、対象ユーザー、目的、支援する理解・判断・行動、現在地、最初の有意味な行動、結果予測、待機・空・失敗・無効時の次行動、反復効率、信頼感を説明します。

## 3. Reviewの基本質問

アプリ本体UIでは次に答えます。GitHub共同作業面だけでは、リポジトリが制御する文言・構造に該当する質問だけを適用します。

1. 誰のためのUIか。
2. そのユーザーは何を達成したいか。
3. 何を理解・判断・実行・回復しやすくするか。
4. 初見で画面目的と現在地が分かるか。
5. 最初の行動と主操作が分かるか。
6. 操作結果を予測できるか。
7. loading、empty、error、disabled、API未設定時に次の行動が分かるか。
8. 慣れたユーザーが不要に遅くならないか。
9. 不必要な不安、恥、責任転嫁、混乱を与えないか。

## 4. Review pipeline

### 4.1 目的・価値

- 対象ユーザーと達成したい結果を特定する。
- UIが助ける判断・行動・理解・回復を明確にする。
- 実装都合の情報や不要な操作を価値として正当化しない。

### 4.2 初見理解

3秒だけ見た前提で、画面目的、現在地、主操作、最初の行動、変化を判断します。実装知識がなければ答えられない箇所は修正候補です。

### 4.3 認知負荷

必要情報を画面へ出し、内部用語や前画面の記憶を要求せず、選択肢を制御し、高度な機能を段階的に開示します。

### 4.4 状態設計

アプリ本体UIでは通常状態だけで判断せず、該当しない理由がない限り、通常、loading、empty、no-results、partial、error、validation-error、disabled、権限不足、offline・API未設定・利用不可、狭幅、文字拡大、長文・大量dataをstate matrixへ記録します。

MJ Prompt StudioではLLM jobのqueued / running / succeeded / failed / cancelled、API key未設定、mock / real API、local asset欠損、DB破損・復旧も関連時に含めます。

GitHub共同作業面では、リポジトリが定義・変更する入力状態だけを確認し、GitHubが所有する未変更のplatform stateは対象外とします。

### 4.5 視覚階層

重要情報と主操作が自然に見え、補助情報が妨げず、grouping、余白、整列、typographyが理解を助けることを確認します。

### 4.6 Accessibility

keyboard、可視focus、自然な順序、accessible name、表示labelとの一致、見出し・landmark、状態通知、contrast、target size、文字拡大、reflow、色以外の手がかりを確認します。

### 4.7 Copy

ユーザーの言葉、結果が分かる動詞、原因・影響・回復を示すerror、次行動を示すempty state、disabledの理由・有効化条件、責任転嫁しないtoneを確認します。ユーザー可視の禁止表記も検査します。

### 4.8 熟練者効率

反復taskの手数、再入力・再選択、入力保持、再試行、前回設定、shortcut、一括操作、復帰を確認し、初心者向け説明が恒常的な障害にならないようにします。

### 4.9 満足感・信頼感

loading、success、failure、delete、external send、LLM解析、data保存、API key、Privacy modeの対象・影響・回復・取り消し可否が誠実に伝わることを確認します。

### 4.10 反証review

実装を落とすつもりで、価値の曖昧さ、初見依存、状態漏れ、accessibility、熟練者効率、信頼を損なう挙動、happy pathだけの証跡を探します。

## 5. P0 / P1 / P2

### P0: 完了不可

- 対象ユーザー、目的、支援価値を説明できない。
- 画面目的、現在地、対象範囲、最初の行動が分からない。
- 主操作が埋もれる、または意味不明なicon-onlyである。
- 主要状態が混ざり、errorに原因・影響・回復がない。
- disabledの理由や有効化条件が分からない。
- keyboard、focus、name / label、contrast、target、構造に重大問題がある。
- 危険操作、削除、外部送信、個人情報、API key、ユーザー資産に予防・確認・回復がない。
- 反復taskが不要な説明、確認、再入力で恒常的に妨害される。
- success、failure、loadingが分からない、またはユーザーを責める。
- 対象面の分類に基づく必須証跡がない。
- 未実行検証を成功扱いする。

### P1: 原則として同じ変更内で修正

- scope、表示優先度、用語が曖昧または不一致。
- empty、success、error後の次行動が弱い。
- 回避可能だが反復手数が多い。
- 説明や警告が冗長で効率・信頼を損ねる。

### P2: Issue化可

微細な余白・文言・順序、将来のshortcutや一括操作、追加説明、実利用調査が必要な改善仮説です。

P0を格下げする場合は、完了不可でない根拠を記録します。

## 6. 数値目安

既存design systemを優先し、なければ通常本文16px以上、長文行高1.5以上、通常text contrast 4.5:1以上、大きい文字・非text部品3:1以上、操作対象24×24 CSS px以上、明確で隠れないfocusを目安とします。

## 7. AI reviewの限界

AI初見simulationは実ユーザーテストではありません。得ていない反応を事実化せず、未実施を明記し、重大な価値・迷い・満足感の仮説は後続検証として残します。
